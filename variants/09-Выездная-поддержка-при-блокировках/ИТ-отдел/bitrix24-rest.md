# REST Bitrix24: что уже можно вызывать

**Кому:** аналитикам и разработчикам контура выезда  
**Портал:** `https://riatpo-service.bitrix24.ru`  
**Точка входа входящего вебхука (офисный контур):** `https://riatpo-service.bitrix24.ru/rest/1/<секрет>/`  
**Секрет в репозиторий не класть.** Боевой вебхук выдаётся на установочной.

Вызовы ниже — штатные методы облака Bitrix24. Их уже использует робот воронки и пара внутренних скриптов линии. Телефон инженера в Зареченске **до этого хоста не достучится**. Вызывать REST должен хост, который видит `bitrix24.ru`.

Авторизация входящего вебхука: секрет в URL, права выданы на `crm`, `task`, `user`, `disk`, `timeline`. Исходящие вебхуки (события портала → наш URL) включить можно; сейчас слушается только `ONCRMDEALUPDATE` на тестовом контуре и никуда дальше не маршрутизируется.

## Общие правила

| Параметр | Значение |
|----------|----------|
| Протокол | HTTPS, JSON |
| Метод | `POST` (допустим `GET` с query, линия так не делает) |
| Успех | HTTP `200` и `"error"` отсутствует |
| Ошибка | объект с `error`, `error_description` |
| Идентификатор сделки | число, в связях задач префикс `D_` |
| Пользователь | числовой `ID` из `user.get` |
| Стадия | строка `C12:…`, см. воронку |
| Дата/время | `YYYY-MM-DDTHH:MM:SS±HH:MM` либо формат портала `DD.MM.YYYY HH:MM:SS` |

Оболочка ошибки:

```json
{
  "error": "ERROR_NOT_FOUND",
  "error_description": "Not found"
}
```

## Сделки

### `crm.deal.get`

Карточка целиком, включая `UF_CRM_12_*`.

```
POST …/crm.deal.get
```

```json
{ "id": 14821 }
```

### `crm.deal.list`

Выборка живых выездов. Фильтр ниже — тот, которым руководитель собирает утренний отчёт.

```json
{
  "filter": {
    "CATEGORY_ID": 12,
    "STAGE_ID": ["C12:VISIT", "C12:ASSIGNED", "C12:ENROUTE", "C12:WAIT_PARTS"],
    "UF_CRM_12_ENGINEER": 31
  },
  "select": [
    "ID", "TITLE", "STAGE_ID", "ASSIGNED_BY_ID",
    "UF_CRM_12_ENGINEER", "UF_CRM_12_ADDRESS", "UF_CRM_12_SLOT",
    "UF_CRM_12_ONSITE", "UF_CRM_12_SYMPTOM", "UF_CRM_12_PARTS",
    "UF_CRM_12_INV", "UF_CRM_12_ACCESS", "UF_CRM_12_SLA",
    "UF_CRM_12_OBJTYPE"
  ]
}
```

### `crm.deal.update`

Движение стадии и запись причины. Смена `STAGE_ID` запускает роботов этой стадии — не двигайте в `VISIT` повторно без нужды, задача уедет второй раз.

```json
{
  "id": 14821,
  "fields": {
    "STAGE_ID": "C12:DONE"
  }
}
```

Для несделки:

```json
{
  "id": 14833,
  "fields": {
    "STAGE_ID": "C12:FAIL",
    "UF_CRM_12_FAIL_REASON": "Допуск объекта закрыт, окно 20:00 просрочено, специалист узнал о заявке в 19:23"
  }
}
```

Переназначение (сейчас делает оператор в UI):

```json
{
  "id": 14819,
  "fields": {
    "UF_CRM_12_ENGINEER": 34
  }
}
```

Само поле задачу не перепривязывает: нужно отдельно обновить `RESPONSIBLE_ID` задачи.

## Задачи

### `tasks.task.add`

Так отрабатывает робот. Повторять из интеграции имеет смысл только если отказались от робота и создаёте задачу сами — **двойных задач на одну сделку линия не хочет**.

```json
{
  "fields": {
    "TITLE": "[Выезд #14821] Касса не фискалит, ТЦ Горизонт",
    "RESPONSIBLE_ID": 31,
    "DEADLINE": "2026-09-07T18:00:00+03:00",
    "DESCRIPTION": "Адрес: …\nОкно: …\nКонтакт: …",
    "UF_CRM_TASK": ["D_14821"],
    "CREATED_BY": 1
  }
}
```

Ответ содержит `result.task.id`.

### `tasks.task.update`

Статус и исполнитель.

Наблюдаемые `STATUS`: `2` — ждет выполнения, `3` — ждет выполнения (после жалоба/контроль, на портале редко), `4` — выполняется, `5` — условно завершена, `6` — отложена.

```json
{
  "taskId": 90211,
  "fields": {
    "STATUS": 5
  }
}
```

Переназначение:

```json
{
  "taskId": 90211,
  "fields": {
    "RESPONSIBLE_ID": 34
  }
}
```

### `tasks.task.get` / `tasks.task.list`

Поиск задачи сделки:

```json
{
  "filter": {
    "UF_CRM_TASK": "D_14821"
  },
  "select": ["ID", "TITLE", "RESPONSIBLE_ID", "STATUS", "DEADLINE", "UF_CRM_TASK"]
}
```

## Таймлайн и файлы

### `crm.timeline.comment.add`

Единственный штатный способ оставить в карточке след «инженер написал из поля», который линия уже умеет читать.

```json
{
  "fields": {
    "ENTITY_ID": 14821,
    "ENTITY_TYPE": "deal",
    "COMMENT": "На объекте. Касса разобрана, жду плату со склада. Источник: Мессенджер Яндекс 360, 08.09 10:02"
  }
}
```

### Вложения

Файлы в облако: `disk.folder.uploadfile` в папку сделки либо `task.item.addfile` / загрузка в диск задачи. Рабочий путь линии сегодня — ручное перетаскивание из чата в карточку. Автоматический приём картинки из Мессенджера **не реализован**. Для концепции: файл, который бот забрал через `messages/getFile`, можно положить на диск портала и привязать к сделке; готового рецепта в проде нет.

Не складывайте код доступа щита в комментарий таймлайна, который видят все наблюдатели сделки. Для поля `UF_CRM_12_ACCESS` отдельное право на просмотр уже уже, чем у таймлайна.

## События (исходящие вебхуки)

Можно включить, сейчас почти не используются.

| Событие | Когда полезно |
|---------|----------------|
| `ONCRMDEALADD` / `ONCRMDEALUPDATE` | сделка вошла в `VISIT` / сменился инженер / сменилась стадия |
| `ONTASKADD` / `ONTASKUPDATE` | робот создал или переназначил задачу |

Тело события — id сущности, не полная карточка. Дальше нужен `crm.deal.get` / `tasks.task.get`. Доставка «at least once»: обработчик обязан быть идемпотентным (повторно не слать инженеру ту же заявку как новую).

Исходящий вебхук стучится на **наш** URL. Этот URL должен быть доступен из облака Bitrix24. Телефон инженера в схеме не участвует.

## Пользователи

```
POST …/user.get
```

```json
{
  "filter": { "ACTIVE": true }
}
```

В ответе есть `ID`, `EMAIL`, `NAME`, `LAST_NAME`, `UF_DEPARTMENT`. Логина Яндекс 360 среди полей **нет**. Соответствие ведётся отдельно (см. воронку).

## Чего в REST нет и придумывать не надо

- Канала «доставить задачу в Мессенджер Яндекс 360» у Bitrix24 нет. Роботы умеют почту, SMS, чат Битрикс — чат Битрикс в белом списке тоже не открывается.
- Отдельной сущности «выезд» нет: это сделка `C12` + задача.
- Нет готового виджета «кнопки статусов для поля». Статусы — `STAGE_ID` и `STATUS` задачи.
