# Bot API Мессенджера Яндекс 360

**Кому:** аналитикам и разработчикам контура выезда  
**Организация:** `riatpo-service.ru`  
**Документация вендора:** [Bot API Мессенджера](https://yandex.ru/dev/messenger/doc/ru/)  
**Админка ботов:** [Боты в Мессенджере](https://admin.yandex.ru/bot-platform)

Бот организации уже создан для пилота, имя в админке: `РИАТПО-Выезд`. В чаты сотрудников его можно писать от лица бота. **Боевой OAuth-токен в репозиторий не класть.**

Боты Яндекс 360 работают **только с сотрудниками организации**. Клиентам на объектах бот ничего не пишет — это внутренний канал.

Базовый хост: `https://botapi.messenger.yandex.net`

Авторизация всех методов:

```http
Authorization: OAuth <токен>
```

Хост API из полевой сети инженера **не нужно** дергать приложением на телефоне: инженер просто открывает Мессенджер (он в белом списке). REST бота вызывает тот же офисный/облачный хост, который ходит в Bitrix24.

## Что бот умеет и зачем это кейсу

| Возможность | Метод | Зачем в контуре выезда |
|-------------|-------|-------------------------|
| Написать сотруднику лично | `POST /bot/v1/messages/sendText/` + `login` | доставить заявку назначенному инженеру, не в общий чат |
| Кнопки быстрого ответа | `suggest_buttons` в том же запросе | «принял / выехал / сделал / не смог / жду ТМЦ» без свободного текста |
| Принять нажатие кнопки | обновление `bot_request` (webhook или polling) | понять, какой статус выбран по какой заявке |
| Принять текст и файл | обновления сообщений | комментарий и фото с объекта |
| Забрать файл | `GET|POST /bot/v1/messages/getFile/` | переложить вложение в Bitrix24 |
| Отправить картинку/файл | `sendImage` / `sendFile` | схема объекта, памятка, если нельзя слать ссылку на портал |
| Создать чат | `POST /bot/v1/chats/create/` | **не основной путь**: ИБ не хочет общие котлы с адресами |
| Редактировать своё сообщение | `sendText` + `message_id` | обновить карточку заявки в том же сообщении при переназначении |

Личное сообщение адресуется **логином** сотрудника (`d.makarov`), не числовым id Bitrix24. Склейка логина и `UF_CRM_12_ENGINEER` — отдельный справочник, см. описание воронки.

У приватного чата нет стабильного `chat_id`, на который можно опереться как на id группы: собеседника определяют по `login` / объекту `User` в обновлении.

## Отправка текста назначенному инженеру

```
POST https://botapi.messenger.yandex.net/bot/v1/messages/sendText/
Content-Type: application/json
Authorization: OAuth <токен>
```

```json
{
  "login": "d.makarov",
  "text": "Выезд #14821. ТЦ Горизонт, касса не фискалит.\nАдрес: ул. Советская 18, пав. 12\nОкно: до 07.09 18:00\nКонтакт: администратор, +7 900 000-00-01\nВезти: плата ФР из склада ЗЧ-12\nИнв.: КС-4412",
  "payload_id": "deal-14821-assign-1",
  "suggest_buttons": {
    "buttons": [
      [{ "text": "Принял", "callback_data": { "deal": 14821, "action": "accept" } }],
      [
        { "text": "Выехал", "callback_data": { "deal": 14821, "action": "enroute" } },
        { "text": "На объекте", "callback_data": { "deal": 14821, "action": "onsite" } }
      ],
      [
        { "text": "Сделал", "callback_data": { "deal": 14821, "action": "done" } },
        { "text": "Не смог", "callback_data": { "deal": 14821, "action": "fail" } },
        { "text": "Жду ТМЦ", "callback_data": { "deal": 14821, "action": "wait_parts" } }
      ]
    ]
  }
}
```

Ограничения вендора, которые уже упёрлись на пилоте:

- `text` — не больше 6000 символов;
- `payload_id` должен быть уникален: повтор с тем же id вендор считает дублем;
- кнопок не больше 100; `inline_keyboard` вендор пометил устаревшим, в новом контуре использовать `suggest_buttons`;
- ссылка на карточку `https://riatpo-service.bitrix24.ru/crm/deal/details/14821/` **бессмысленна в поле**: портал не откроется. Не стройте сценарий «нажми ссылку и работай в CRM».

Нужно ли класть в текст код щита (`UF_CRM_12_ACCESS`) — вопрос к заказчику и ИБ, не к API. Технически поле уйдёт как обычная строка.

## Получение ответов

Два взаимоисключающих режима: **webhook** или **polling**. Одновременно вендор держать не рекомендует.

### Webhook

В админке бота или методом обновления бота задаётся `webhook_url`. Дальше Яндекс шлёт `POST` с телом как у `messages/getUpdates`. Гарантия — at least once, порядок сохраняется в паре бот+чат, ретраи до 24 часов.

URL вебхука должен быть доступен **из интернета Яндекса**. Офисный сервер за NAT без публикации не подойдёт — нужен явный вход (как и для исходящих вебхуков Bitrix24).

### Polling

```
POST https://botapi.messenger.yandex.net/bot/v1/messages/getUpdates/
```

Подходит для стенда. Для продакшена линия хочет webhook, чтобы статус «принял» не ждал опроса.

В обновлении смотреть:

- обычное сообщение инженера — текст или файл (фото акта);
- `bot_request`, если нажата кнопка с серверным действием / `callback_data`;
- автор — объект пользователя, сверять с логином назначенного, не принимать статус заявки 14821 от чужого сотрудника.

Готовой схемы «кнопка сразу двигает стадию в Bitrix24» нет. Это как раз то, что нужно спроектировать: что считается приёмом, что — закрытием, что делать, если пришла фотография без нажатой кнопки, что делать с свободным текстом «сейчас подойду».

## Файлы

Инженер кидает фото в личку с ботом. В обновлении приходит `file_id`. Забрать байты:

```
POST https://botapi.messenger.yandex.net/bot/v1/messages/getFile/
Authorization: OAuth <токен>
```

```json
{ "file_id": "<id>" }
```

Ответ — поток файла. Кладёте его в диск/таймлайн Bitrix24 сами. Обратной готовой трубы нет.

Отправка картинки инженеру (схема проезда, шильдик с эталона) — `POST /bot/v1/messages/sendImage/`, `multipart`, поле `login` или `chat_id`.

## Создание группового чата

```
POST https://botapi.messenger.yandex.net/bot/v1/chats/create/
```

Обязательны `name`, `description`. Можно сразу добавить `members` (до 50 за раз) и `admins`.

ИБ и руководитель в переписке уже сказали, что общий чат «Выезд / Зареченск» как канал постановки **провалился**. Метод существует, но это не приглашение «давайте все заявки в одну группу». Если предлагаете групповой чат — объясните, зачем он, если персональная доставка по `login` уже есть.

## Ограничения, которые всплывут на встрече

- Бот не пишет людям вне организации 360. Подрядчик «на один выезд» без логина в `riatpo-service.ru` канал не получит.
- Если у сотрудника не заведён аккаунт 360 или он не принял оферту мессенджера — `sendText` по логину не доставит заявку. Кадровый разрыв (есть в Bitrix24, нет в 360) надо явно обработать: иначе офис снова решит, что «задача ушла».
- Инженер может быть без сети в подвале объекта: сообщение догонит его, когда Мессенджер снова выйдет в сеть. Это не мгновенный push Bitrix24 «как в офисе», но в городе с фильтром это единственный живой канал.
- Редактирование чужих сообщений инженера бот не делает. Свою карточку заявки — может обновить через `message_id`.

Официальные методы и типы — в индексе вендора: [llms.txt](https://yandex.ru/dev/messenger/doc/ru/llms.txt). Этот файл не заменяет документацию, а фиксирует, **что из неё уже доступно нашей организации и как это стыкуется с запретом открывать Bitrix24 в поле**.
