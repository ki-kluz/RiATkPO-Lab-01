# Воронка CRM и выездные задачи в Bitrix24

**Портал:** `https://riatpo-service.bitrix24.ru`  
**Раздел:** CRM → Сделки → воронка «Сервис / обращения»  
**Категория сделок:** `C12`  
**Связанные задачи:** робот на стадии `C12:VISIT` создаёт задачу и вешает её на полевого инженера

Это описание **текущего** учёта бесконтактной линии. Полевой специалист в заблокированном городе этот интерфейс не видит. Менять состав стадий «потому что так удобнее чату» без согласования заказчика нельзя: по воронке считаются SLA и премии линии.

## Как заявка появляется

1. Обращение приходит на бесконтактную линию: телефония, почта, форма на сайте. Создаётся сделка в стадии `NEW`.
2. Оператор квалифицирует: закрывается удалённо или нужен выезд.
3. Если нужен выезд, оператор заполняет поля выезда (адрес, окно, что везти) и двигает сделку в `VISIT`.
4. Робот стадии создаёт задачу, исполнитель = значение поля «Выездной специалист».
5. Дальше по задумке инженер ведёт задачу и двигает сделку. По факту в Зареченске / Октябрьском шаг 5 не выполняется.

Тип сущности учёта — **сделка**, не лид. Лид используется только на входе маркетинга и в этот контур не входит.

## Стадии воронки `C12`

| STAGE_ID | Название в интерфейсе | Кто двигает сейчас | Смысл |
|----------|----------------------|--------------------|--------|
| `C12:NEW` | Новое обращение | робот / оператор | первичная карточка |
| `C12:QUAL` | Квалификация | оператор бесконтактной линии | уточнение, удалённая попытка |
| `C12:REMOTE` | Закрыто удалённо | оператор | выезд не нужен |
| `C12:VISIT` | Нужен выезд | оператор | обязательны поля выезда; здесь срабатывает робот задачи |
| `C12:ASSIGNED` | Назначен специалист | робот (после создания задачи) | заявка «уехала» в задачу; **здесь зависает поле** |
| `C12:ENROUTE` | В пути / на объекте | по регламенту — инженер | почти никогда не обновляется из города |
| `C12:DONE` | Выполнено | по регламенту — инженер, факт — руководитель руками | нужен комментарий и вложения |
| `C12:WAIT_PARTS` | Ожидание ТМЦ | инженер / руководитель | не провал, пауза SLA по правилу склада |
| `C12:FAIL` | Не выполнено | инженер / руководитель | обязательна причина |
| `C12:WON` | Закрыто (успех) | оператор после проверки | финал, акт/отчёт принят |
| `C12:LOSE` | Закрыто (отказ / срыв) | руководитель | клиентский срыв, повторный выезд — новая сделка |

Семантика успеха/провала для API: `WON` и `LOSE` — терминальные. `DONE` ещё проверяет линия. Двигать сделку назад (например, с `ASSIGNED` в `QUAL`) операторам можно, роботу поля — только по явному сценарию переквалификации.

## Поля сделки, которые нужны выезду

Штатные и пользовательские поля, которые робот копирует в описание задачи. Пустое обязательное поле на входе в `VISIT` робот не пропускает — сделка остаётся в `QUAL` с комментарием робота.

| Поле | Код | Обязательно на `VISIT` | Комментарий |
|------|-----|------------------------|-------------|
| Название | `TITLE` | да | обычно «Адрес — симптом» |
| Ответственный линии | `ASSIGNED_BY_ID` | да | оператор, не инженер |
| Выездной специалист | `UF_CRM_12_ENGINEER` | да | пользователь портала, id как в `user.get` |
| Адрес объекта | `UF_CRM_12_ADDRESS` | да | строка, без геокодера |
| Окно допуска | `UF_CRM_12_SLOT` | да | текст, например `09.09 09:00–11:00, допуск до 20:00` |
| Контакт на объекте | `UF_CRM_12_ONSITE` | да | ФИО и телефон |
| Симптом / что делать | `UF_CRM_12_SYMPTOM` | да | |
| Что везти | `UF_CRM_12_PARTS` | нет | ЗИП, ключи, расходники |
| Инвентарный / серийный | `UF_CRM_12_INV` | нет | часто отсутствует, линия уточняет |
| Код доступа / щит | `UF_CRM_12_ACCESS` | нет | **нельзя светить в групповых чатах** |
| SLA до | `UF_CRM_12_SLA` | да | datetime; из него робот ставит `DEADLINE` задачи |
| Тип объекта | `UF_CRM_12_OBJTYPE` | да | касса / СКУД / АРМ / серверная / иное |
| Причина несделки | `UF_CRM_12_FAIL_REASON` | на `FAIL` | иначе стадию не принимают в отчёте |

Компания и контакт CRM (`COMPANY_ID`, `CONTACT_ID`) заполняются на квалификации. В поле инженеру их целиком не отдают.

## Задача, которую ставит робот

Робот стадии `C12:VISIT` (имя в интерфейсе: «Создать выездную задачу»):

- метод по сути тот же, что `tasks.task.add`;
- `TITLE` = `[Выезд #{ID сделки}] {TITLE}`;
- `RESPONSIBLE_ID` = `UF_CRM_12_ENGINEER`;
- `DEADLINE` = `UF_CRM_12_SLA`;
- `DESCRIPTION` — склейка адреса, окна, контакта, симптома, ЗИП, инвентарного, кода доступа;
- `UF_CRM_TASK` = `D_{ID сделки}`;
- постановщик — технический пользователь `user_id = 1` (робот).

После создания робот пишет в таймлайн сделки комментарий `Задача {id} назначена` и двигает стадию в `C12:ASSIGNED`.

Отдельного мобильного сценария «инженер нажал кнопку в задаче → стадия сделки» нет. Регламент бумажный: инженер меняет статус задачи (`3` ждёт / `4` выполняется / `5` условно завершена) и стадию сделки руками. В поле это не выполняется.

Переназначение: оператор меняет `UF_CRM_12_ENGINEER` и `RESPONSIBLE_ID` задачи. Событие в портале есть, **канала в Мессенджер нет**.

## SLA (как считает отчёт линии)

| Тип объекта | Норматив до прибытия с момента `VISIT` | Фото при закрытии |
|-------------|----------------------------------------|-------------------|
| Касса / фискальная техника | 4 рабочих часа | шильдик + факт работы (чек / экран) |
| СКУД / турникет | 6 рабочих часов | общий план + узел |
| АРМ / оргтехника | 8 рабочих часов | не обязательно |
| Серверная | 4 рабочих часа | по регламенту заказчика |

«Рабочие часы» линии: 08:00–20:00, пн–сб. Ночной робот задачи создаёт, линия не дежурит. Поле об этом из Bitrix24 не узнаёт.

## Что уже ломается на цифрах (выгрузка 01–07.09.2026)

ИТ снял с портала, не приукрашивая:

- 214 сделок дошли до `VISIT`;
- 181 получили задачу и стадию `ASSIGNED`;
- **126 из 181** к исходу следующих суток всё ещё в `ASSIGNED` при просроченном `UF_CRM_12_SLA`;
- у 74 из этих 126 руководитель позже руками проставил `DONE` или `FAIL` по переписке / звонку;
- вложений в задаче нет у 91 закрытой «задним числом» сделки;
- расхождение «кто в поле считает, что сделал» и «что в воронке» — предмет жалобы в выгрузке чата.

Это не KPI будущего решения, а картина «как есть» для границ кейса.
